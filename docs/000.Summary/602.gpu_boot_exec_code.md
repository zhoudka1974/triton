# GPU 启动器与内核执行代码

> 分析 Triton 中 CUDA/HIP 启动器的 C/C++ 代码生成、二进制加载、内核执行机制
> 覆盖 NVIDIA GPU 和 AMD GPU

---

## 整体架构

```
Python Triton (jit.py / compiler.py)
    │
    ├─ make_launcher()  ─── 运行时动态生成 C 启动器代码
    │   │
    │   └─ compile_module_from_src() ─── 编译为 Python C 扩展 (.so)
    │
    ├─ CudaLauncher / HIPLauncher ─── 启动器实例
    │   │
    │   ├─ launch() ─── 解析参数 → getPointer() → _launch()
    │   │
    │   └─ _launch() ─── cuLaunchKernel / hipModuleLaunchKernel
    │
    ├─ driver.c ─── C 工具函数 (加载二进制, 设备属性)
    │   │
    │   └─ loadBinary() ─── cuModuleLoadData / hipModuleLoadDataEx
    │
    └─ cubin / hsaco ─── GPU 可执行二进制
```

## 一、二进制加载（GPU 可执行代码加载到显存）

### 1.1 Python 入口

**软件包：Triton** | **文件：`python/triton/compiler/compiler.py`**

#### `CompiledKernel._init_handles` — 第 436~463 行

```python
def _init_handles(self):
    # 加载编译后的 GPU 二进制（cubin/hsaco）到 CUDA/HIP 环境
    self.module, self.function, self.n_regs, self.n_spills, self.n_max_threads = \
        driver.active.utils.load_binary(
            self.name, self.kernel, self.metadata.shared, device)
```

**参数**：
- `self.name`：内核函数名（字符串）
- `self.kernel`：编译后的 GPU 二进制字节流（`.cubin` / `.hsaco`）
- `self.metadata.shared`：共享内存大小
- `device`：GPU 设备索引

**返回值**：
- `module`（`CUmodule` / `hipModule_t`）：GPU module 句柄
- `function`（`CUfunction` / `hipFunction_t`）：GPU 内核函数句柄
- `n_regs`：寄存器使用数
- `n_spills`：local memory 使用量
- `n_max_threads`：每 block 最大线程数

### 1.3 NVIDIA `loadBinary()` C 函数

**软件包：Triton** | **文件：`python/triton/backends/nvidia/driver.c` 第 102~164 行**

```c
static PyObject *loadBinary(PyObject *self, PyObject *args) {
  const char *name;        // 内核函数名
  const char *data;        // cubin 二进制数据
  Py_ssize_t data_size;
  int shared;
  int device;

  PyArg_ParseTuple(args, "ss#ii", &name, &data, &data_size, &shared, &device);

  CUfunction fun;
  CUmodule mod;

  // ★ 第 128 行: 将 cubin 加载为 CUDA module（放入 GPU 显存）
  CUDA_CHECK_AND_RETURN_NULL_ALLOW_THREADS(
      cuModuleLoadData(&mod, data));

  // ★ 第 129-130 行: 从 module 中获取内核函数句柄
  CUDA_CHECK_AND_RETURN_NULL_ALLOW_THREADS(
      cuModuleGetFunction(&fun, mod, name));

  // 第 132-138 行: 查询内核属性
  cuFuncGetAttribute(&n_regs, CU_FUNC_ATTRIBUTE_NUM_REGS, fun);
  cuFuncGetAttribute(&n_spills, CU_FUNC_ATTRIBUTE_LOCAL_SIZE_BYTES, fun);
  cuFuncGetAttribute(&n_max_threads, CU_FUNC_ATTRIBUTE_MAX_THREADS_PER_BLOCK, fun);

  // 第 154-155 行: 设置动态共享内存大小
  cuFuncSetAttribute(fun, CU_FUNC_ATTRIBUTE_MAX_DYNAMIC_SHARED_SIZE_BYTES, shared);

  return Py_BuildValue("(KKiii)", (uint64_t)mod, (uint64_t)fun,
                       n_regs, n_spills, n_max_threads);
}
```

| 行号 | CUDA API | 作用 |
|------|----------|------|
| 128 | `cuModuleLoadData(&mod, data)` | 将 cubin 加载为 CUmodule（放入 GPU 可执行空间） |
| 129-130 | `cuModuleGetFunction(&fun, mod, name)` | 按名字获取内核函数句柄 CUfunction |
| 133 | `cuFuncGetAttribute(NUM_REGS)` | 查询寄存器数 |
| 135 | `cuFuncGetAttribute(LOCAL_SIZE_BYTES)` | 查询 local memory 使用量 |
| 137-138 | `cuFuncGetAttribute(MAX_THREADS_PER_BLOCK)` | 查询每 block 最大线程数 |
| 154-155 | `cuFuncSetAttribute(MAX_DYNAMIC_SHARED_SIZE)` | 设置动态共享内存上限 |

**NVIDIA vs AMD 差异**：

| 步骤 | NVIDIA CUDA API | AMD HIP API | 行号 |
|------|----------------|-------------|------|
| 加载二进制 | `cuModuleLoadData(&mod, data)` | `hipModuleLoadDataEx(&mod, data, ...)` | 128 / 346 |
| 获取函数 | `cuModuleGetFunction(&fun, mod, name)` | `hipModuleGetFunction(&fun, mod, name)` | 129 / 348 |
| 查寄存器数 | `cuFuncGetAttribute(NUM_REGS)` | `hipFuncGetAttribute(NUM_REGS)` | 133 / 353 |
| 设共享内存 | `cuFuncSetAttribute(...)` | 不适用 | 154 / - |

```c
// ─────────────────────────────────────────────
// 生成的 C 启动器源码 (由 make_launcher() 一次性生成)
// 包含三个主要部分: launch() + _launch() + getPointer()
// ─────────────────────────────────────────────

// === Part 1: getPointer() — 提取 GPU 设备指针 ===
static inline DevicePtrInfo getPointer(PyObject *obj, int idx) {
  ...
}

// === Part 2: _launch() — 封装 CUDA Driver API ===
// 纯 C 原生类型参数，不涉及 Python C API
static void _launch(int gridX, int gridY, int gridZ, int num_warps, int num_ctas,
                    int launch_cooperative_grid, int shared_memory,
                    CUstream stream, CUfunction function, ...) {
  void *params[] = { ... };  // GPU 指针 + 标量值
  cuLaunchKernel(function, gridX, gridY, gridZ, ...);
}

// === Part 3: launch() — Python C 扩展入口 ===
// 符合 PyCFunction 签名，负责解析 Python 参数
static PyObject* launch(PyObject* self, PyObject* args) {
  ensureCudaContext();

  // 解析 Python 参数 -> C 类型
  PyArg_ParseTuple(args, "iiiKKppOOOO...", &gridX, &gridY, &gridZ, ...);

  // 调用 getPointer() 提取 GPU 地址
  DevicePtrInfo ptr_0 = getPointer(arg_0, 0);
  DevicePtrInfo ptr_1 = getPointer(arg_1, 1);
  int32_t scalar_0 = PyLong_AsLong(arg_3);

  // 调用 _launch() 执行 CUDA 启动
  _launch(gridX, gridY, gridZ, num_warps, num_ctas, ...,
          ptr_0.dev_ptr, ptr_1.dev_ptr, scalar_0, ...);

  Py_RETURN_NONE;
}
```

**`launch()` 和 `_launch()` 的关系**：

两者处在**同一个生成的 C 源文件中**，是调用者和被调用者的关系：

| 函数 | 角色 | 签名 | 负责 |
|------|------|------|------|
| `launch()` | Python 入口 | `(PyObject* self, PyObject* args)` | 解析 Python 参数、提取 GPU 指针 |
| `_launch()` | CUDA 调用 | `(int, int, ..., CUstream, CUfunction, ...)` | 调用 `cuLaunchKernel` |

**为什么分成两个函数？** 因为 `launch()` 必须符合 Python C 扩展的 `PyCFunction` 签名（返回 `PyObject*`）。它负责把 Python 传进来的 `PyObject*` 参数解析为 C 原生类型，然后交给 `_launch()` 执行真正的 CUDA 启动。分成两个函数让 `_launch()` 保持纯 CUDA 语义，不被 Python C API 的细节污染。

### 2.4 `_launch()` — CUDA 内核启动 — 生成 C 代码第 462~487 行

```c
static void _launch(int gridX, int gridY, int gridZ, int num_warps, int num_ctas,
                    int launch_cooperative_grid, int shared_memory,
                    CUstream stream, CUfunction function, ...) {
  void *params[] = { ... };  // 参数数组（GPU 指针 + 标量值）

  if (num_ctas > 1)
    cuLaunchKernelEx(&config, function, params, 0);
  else if (launch_cooperative_grid)
    cuLaunchCooperativeKernel(function, gridX, gridY, gridZ,
        num_warps*32, 1, 1, shared_memory, stream, params);
  else
    cuLaunchKernel(function, gridX, gridY, gridZ,
        num_warps*32, 1, 1, shared_memory, stream, params);
}
```

**三种启动模式**：

| 模式 | CUDA API | 条件 |
|------|----------|------|
| 标准启动 | `cuLaunchKernel` | 默认 |
| 协同启动 | `cuLaunchCooperativeKernel` | `launch_cooperative_grid = True` |
| CTA 集群 | `cuLaunchKernelEx` | `num_ctas > 1`（SM90+ Hopper） |

## 四、启动器缓存机制

**软件包：Triton** | **文件：`python/triton/runtime/build.py` 第 59~97 行**

`compile_module_from_src()` 有**两层缓存**：

### 4.1 内存缓存

```python
@functools.lru_cache     # 内存 LRU 缓存
def compile_module_from_src(src, name, ...):
```

同一个 `src` 字符串在进程内只编译一次。

### 4.2 磁盘缓存

```python
cache = get_cache_manager(key)             # 根据源码哈希
cache_path = cache.get_file(f"{name}.so")  # 检查磁盘缓存
if cache_path is not None:
    return _load_module_from_path(name, cache_path)  # 直接加载

# 首次才真正编译:
with tempfile.NamedTemporaryFile(...) as f:
    ...  # 调用 C 编译器
    cache.put(f.read(), f"{name}.so", binary=True)   # 缓存到磁盘
```

### 4.3 生命周期

```
第一次运行某个内核:
  生成 C 启动器源码 → 编译 .so → 写入磁盘缓存 → 加载到 Python 进程

第二次运行（同签名）:
  内存 LRU 缓存命中 → 直接返回（不编译、不读磁盘）

新进程（同签名）:
  磁盘缓存命中 → 直接加载 .so（不编译）

内核签名变化时:
  新 C 代码 → 新编译 → 新缓存
```

每个 `@triton.jit` 函数 × 每种参数特化，各自生成不同的启动器 C 代码，各自缓存。

## 六、GPU 二进制格式与生成
